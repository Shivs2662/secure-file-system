# Secure File Management & Storage System
**DBMS + Operating Systems PBL** — Java 17 · Spring Boot 3 · MySQL 8 · HTML/CSS/JS (glassmorphism UI)

A small multi-user "Drive": folders, upload/download, sharing with read/write permissions, write locks,
versions, audit trail — plus two OS labs:
* **File allocation** (contiguous / linked / indexed) on a simulated **200-block disk** (8 KB blocks)
* **Disk scheduling** (FCFS / SSTF / SCAN / C-SCAN) with head-path charts and a 4-way comparison

> **OS decides HOW** (allocation + scheduling classes are pure Java, no DB) — **DBMS records WHAT happened**
> (block map, permissions, locks, versions, requests, results — all written in one transaction).

## 1. Run it
1. Install JDK 17+, Maven, MySQL 8.
2. MySQL Workbench → open `db/schema.sql` → run the whole script (creates DB `secure_file_system`, tables, views, procedures, triggers).
3. Edit `src/main/resources/application.properties` → set `spring.datasource.username/password`.
4. `mvn spring-boot:run`  → open **http://localhost:8080**
5. Login with the seeded admin: **admin / Admin@123** (change in `application.properties` first). Register a second user to test sharing.
6. `mvn test` runs the algorithm unit tests (they assert the report's 642 / 208 / 332 / 391 results).

## 2. Where each report concept lives
| Concept | Code |
|---|---|
| Contiguous / Linked / Indexed allocation | `service/allocation/*AllocationService.java` (interface `AllocationStrategy`) |
| FCFS / SSTF / SCAN / C-SCAN | `service/scheduling/*SchedulingService.java` (interface `SchedulingStrategy`) |
| Upload as one ACID transaction (+ retry if two uploads race for a block) | `FileService.upload / doUpload` |
| `UNIQUE(block_no)` guarantees no two files share a block | `db/schema.sql` → `File_Blocks` |
| Write lock = `SELECT … FOR UPDATE` on the file row, then check/insert | `FileLockService.acquire`, `FileRepository.lockById` |
| Lock timeout / crash recovery | `FileLockService.cleanupExpired` (every 60 s), `sfs.lock.minutes` |
| Versioning (restore = new version) | `FileService.doNewVersion / restore`, `File_Versions` |
| Permission checks on every call | `PermissionService` |
| Triggers (audit, permission, version) / views / stored procedures | bottom of `db/schema.sql` |
| Disk requests generated by file access | `DiskRequestService` → `Disk_Requests` → "use pending queue" in the Scheduling Lab |

## 3. Demo script (≈10 min)
1. Login → Dashboard (disk map, fragmentation %).
2. My Files → New folder → Upload `report.pdf` as **Contiguous**; upload two more as **Linked** and **Indexed**; open each file → *Disk blocks* tab.
3. Allocation Lab → dry-run 5 contiguous blocks; delete a file in the middle, upload again and watch fragmentation.
4. Second browser (private window): register `bob`. As admin user: file → *Share* → bob, write ✓.
5. As bob: *Shared with me* → file → *Edit & lock* → acquire lock. As the owner try to lock → **409 FILE_LOCKED**.
6. Bob saves → v2 (lock released) → *Versions* → restore v1 (needs lock) → becomes v3.
7. Scheduling Lab → `50 / 82,170,43,140,24,16,190` → **Compare all 4** (642 / 208 / 332 / 391). Then tick *use pending disk queue* to schedule the requests your own file opens generated.
8. Workbench: `SELECT * FROM File_Blocks; SELECT * FROM File_Locks; SELECT * FROM vw_scheduling_performance; SELECT * FROM Audit_Logs ORDER BY audit_id DESC;`
9. Admin → Audit Logs / Users.

## 5. Honest notes / limitations
* The disk is **simulated**: file bytes are stored under `./storage/{fileId}/v{n}`; the 200-block map in MySQL is the OS model.
* Security is coursework-grade: BCrypt, server-side authorization, parameterised queries, extension allow-list, size limit, audit logs.
  **CSRF protection is disabled** (same-origin SPA, kept simple); add it before any real deployment. No encryption at rest, no virus scanning.
* Locking is application-level (DB-backed), not kernel `flock`. Lock holder crash → lock expires after 30 min.
* The stored procedures/triggers in `schema.sql` mirror the report; the Java code does the same work through JPA, except the
  triggers, which fire automatically (FILE_CREATED, PERMISSION_GRANTED/CHANGED, FILE_VERSIONED audit rows).
* Deviation from the report: the "bump `current_version` on size change" trigger was replaced by an audit trigger, because a same-size edit would
  not bump the version; the service now owns version numbers.
* Max upload 1 MB (`spring.servlet.multipart.*`). Raise `sfs.disk.blocks` / `block-size` if you want bigger files.
